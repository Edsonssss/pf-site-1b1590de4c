# Ежедневное автообновление прогнозов Т-Банка (daily-update)

Прогнозы больше не нужно переносить вручную из чата: каждый будний день
workflow `daily-update` сам забирает **сводный прогноз Т-Банка** (консенсус
аналитиков: рекомендация, средняя целевая цена, диапазон min–max, число
аналитиков) через официальный **T-Invest API** (`InstrumentsService/
GetConsensusForecasts`) и обновляет его в `portfolio_data.json`, на страницах
сайта и в Excel.

Версия этого скрипта на scraping страниц tbank.ru (`/invest/stocks/<тикер>/`)
перестала работать: Т-Банк отвечал `HTTP 429: Too Many Requests` после
нескольких страниц. API-версия решает это: карта тикеров строится одним
запросом `GetAssets` (в ответе каждый актив несёт свой assetUid и список
своих инструментов с тикерами), консенсусы приходят постранично (страницы
по 200 записей); при сбоях — ретраи, а резервная карта строится отдельными
маленькими запросами `FindInstrument`.

## Какие файлы скопировать в репозиторий (заменить все три)

| Файл | Куда положить | Что изменилось |
| --- | --- | --- |
| `fetch_forecasts.py` | **корень репо** (рядом с `auto_update.py`) | T-Invest API; встроенные сертификаты НУЦ (TLS); карта тикеров через `GetAssets` (ключ консенсуса — assetUid, реестр активов); ретраи на обрывы ответа; FindInstrument как резерв |
| `daily-update.yml` | `.github/workflows/daily-update.yml` — заменить | Шаг прогнозов теперь передаёт `TB_TOKEN` |
| `make_excel.py` | корень репо — заменить | Дата прогноза и список «без прогноза» динамические |

Важно: обновить нужно **и скрипт, и workflow вместе** — в новом workflow шаг
прогнозов передаёт secret `TB_TOKEN` (тот же секрет, что для выгрузки
портфеля; менять его не надо).

## Одноразовое действие: переименование Excel

Excel собирается под постоянным именем **`Портфель_и_прогнозы_ТБанк.xlsx`**
(дата прогноза — внутри файла, в шапке и на листе «Сводка»). Старый
`Портфель_и_прогнозы_ТБанк_08.10.2026.xlsx` удалите из репозитория один раз
(GitHub web: открыть файл → корзина → Commit).

## Порядок шагов в workflow

1. `fetch_forecasts.py` — свежие цели/рекомендации в `portfolio_data.json`
   (2–5 запросов к API с ретраями на 429/5xx).
2. `auto_update.py` — цены MOEX, паи, дивиденды; пересчитывает потенциал
   (upside) уже от свежих целей, пересобирает `portfolio_data.js` и
   встроенный JSON в `index.html`.
3. `make_excel.py` — пересборка Excel.
4. Коммит и push (как раньше).

Расписание не менялось: пн–пт в 23:45 МСК (`cron '45 20 * * 1-5'`), плюс
кнопка **Run workflow** для ручного запуска.

## Запуск вручную на своём компьютере

Нужен read-only токен T-Invest API (тот же, что в secret TB_TOKEN):

```bash
export TB_TOKEN="t.xxxxx"        # Linux/Mac
python3 fetch_forecasts.py
```
```bat
set TB_TOKEN=t.xxxxx             :: Windows cmd
python fetch_forecasts.py
```
```powershell
$env:TB_TOKEN="t.xxxxx"          # Windows PowerShell
python fetch_forecasts.py
```

## Что обновляется, а что нет

- Обновляется: `target_price`, `range_min`/`range_max`, `recommendation`
  (Покупать/Держать/Продавать), `n_forecasts` (число аналитиков в консенсусе),
  `prognosis_date` (дата прогноза Т-Банка), `upside_pct`,
  `summary.recommendations` (счётчики buy/hold/sell), `meta.forecasts_date`.
- Не трогается: количества бумаг, дивиденды, примечания (`note`), FEES и PMSB
  (по ним в Т-Банке консенсуса нет), облигация RU000A10C5L7 (ISIN — пропускается).

## Как проверить после копирования

1. Actions → **daily-update** → Run workflow → дождаться зелёного.
2. В логе шага «update forecasts (tbank consensus)» — строка карты тикеров
   (`карта тикеров: GetAssets (26 из 26)`) и таблица вида:
   `SBER: Покупать, цель 383.8 ₽ [320 — 430], аналитиков 14  (было 379.4)`,
   в конце — строка `обновлено прогнозов: N | цели изменились: M`.
3. В `portfolio_data.json` — `meta.forecasts_date` = дата запуска.

## Если что-то пошло не так

- `CERTIFICATE_VERIFY_FAILED: self-signed certificate in certificate chain` —
  на раннере GitHub Actions нет корневого сертификата НУЦ Минцифры
  (Russian Trusted Root CA), а Т-Банк отдаёт цепочку с ним. Это исправлено в
  актуальном `fetch_forecasts.py`: сертификаты НУЦ встроены в сам скрипт
  (ничего доустанавливать не нужно). Если такое увидели — просто замените
  `fetch_forecasts.py` в репозитории на актуальный и перезапустите workflow.
- `Ошибка API ... HTTP 404` — старая версия скрипта обращалась к шлюзу через
  слэш; правильный путь — через точку
  (`…contract.v1.InstrumentsService/Shares`). Тоже исправлено в актуальной
  версии — обновите `fetch_forecasts.py`.
- Строка в логе `TLS: строгая проверка сертификата (системные CA + НУЦ)` —
  нормальный режим, ничего делать не надо.
- Строка `TLS: строгая проверка не прошла — соединение БЕЗ проверки
  сертификата (резервный режим)` — обновление продолжится, но строгую проверку
  TLS включить не удалось: запустите workflow повторно; если повторяется —
  обновите `fetch_forecasts.py` до актуальной версии.
- `Ошибка: не задан токен` — workflow не передал `TB_TOKEN`: проверьте, что в
  репозиторий скопирован и новый `daily-update.yml` (env в шаге прогнозов).
- `HTTP 401/403 ... Токен неактуален или нет доступа` — перевыпустите токен
  в Т-Банке (права на «рыночные данные» / «Портфель») и обновите secret.
- `ВНИМАНИЕ: консенсус не загружен (IncompleteRead...)` — старая версия
  скрипта тянула карту всех инструментов одним 3 МБ-запросом, и передача
  обрывалась на середине. В актуальной версии карта строится маленькими
  запросами `FindInstrument` по каждому тикеру, обрывы повторяются ретраем,
  а обрыв отдельной страницы консенсуса не теряет уже собранные страницы.
  Замените `fetch_forecasts.py` на актуальный и перезапустите workflow.
- `ВНИМАНИЕ: страница консенсуса №N не прочитана (...) — работаем с
  частичными данными` — обновление прошло по уже собранным страницам;
  тикеры с ненагрузившейся части оставили прежние прогнозы. Если повторяется
  от запуска к запуску — запустите workflow ещё раз (сбой разовый).
- `обновлено прогнозов: 0 | ... | без консенсуса: <все тикеры>` + блок
  `ДИАГНОСТИКА: записи консенсуса есть, но ни один UID не совпал` — у записи
  консенсуса поле `uid` — это ID **самой записи**, а инструмент определяется
  полем **`assetUid`** (UID актива из реестра активов, который отдельный от
  реестра инструментов). В актуальной версии карта тикеров строится запросом
  `GetAssets` (актив → assetUid + его инструменты с тикерами), сопоставление
  идёт по assetUid, повторные записи схлопываются по свежей дате, консенсус
  в иностранной валюте (не rub) не переносится в рублёвый портфель.
  Замените `fetch_forecasts.py` на актуальный и перезапустите workflow.
  Если блок `ДИАГНОСТИКА:` появится снова — пришлите его целиком: теперь там
  печатаются и assetUid тикера, и instrumentUid, и первые ключи записей —
  по этому фрагменту видно, какие идентификаторы с какой стороны.
- `GetAssets не удался (...) — строим карту через FindInstrument` — большой
  ответ списка активов оборвался даже после ретраев; скрипт перешёл на
  резервную карту. В ней нет assetUid, поэтому консенсусы, скорее всего,
  не совпадут (прогнозы останутся прежними), но конвейер продолжится.
  Обычно повторный запуск проходит — сбой передачи разовый.
- Конвейер прогнозов не блокирует шаги цен: при любом сбое консенсуса
  обновление цен, истории и Excel продолжается.
